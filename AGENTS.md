# AERIS agent contract

Read `docs/START_HERE.md`, `docs/PROJECT_STATE.md`, `docs/CONTRACTS.md`, and the
task packet generated by `python3 tools/orchestrate.py prepare TASK-ID` before work.
The repository is the durable memory. Chat history is not an authoritative spec.

## Execution
- Work on one ready task at a time. Follow its dependencies, acceptance criteria,
  write scope, and required checks in `orchestration/tasks.json`.
- Use `rtk` for shell commands when installed (user instruction in
  `/Users/vincenzo/.codex/RTK.md`). If absent, report that once and use raw commands.
- Never fabricate metrics, test output, dataset access, model quality, or completed work.
- A scaffold, mock detector, or synthetic fixture is not a real perception benchmark.
- Keep runtime inputs separate from labels, future observations, and simulation truth.
- Do not change gates, contracts, test expectations, or baseline thresholds to make
  your task pass. Propose a separate contract-change task with rationale and review.
- Do not install heavy dependencies, download datasets, train models, or rent compute
  unless within the current task's explicit scope and resource budget.
- No credentials, dataset contents, checkpoints, or videos in Git. Record checksums,
  provenance, licenses, manifests, and reproducible retrieval instructions instead.
- Use timestamp deltas, original-frame pixel coordinates, and explicit units.
- Unknown measurements stay null with a reason. Do not invent confidence intervals.
- No autonomous targeting, weapons integration, or control outputs are in project scope.

## Quality and handoff
- Write implementation reports using the generated `report.json` template.
- Every acceptance criterion needs an artifact path and a concrete explanation.
- Report failures and unrun checks. Run checks with `verify`; prose is not evidence.
- A fresh reviewer must inspect the actual patch, tests, and evidence. The author
  cannot review their own result. Separate agent sessions are an operational rule;
  identity strings in the tool are not authentication.
- At most three attempts per task. Escalate repeated failures with the smallest
  reproducer, suspected cause, options, and next decision. Never loop indefinitely.
- The coordinator alone accepts tasks. Acceptance requires current verified contents
  and a passing independent review, then updates durable state.
- Do not launch parallel writers in one checkout. For later parallel work, use isolated
  worktrees and disjoint ownership; re-run verification on the integrated checkout.
- Before context compaction or stopping, complete the report's handoff fields:
  decisions, unresolved issues, exact next action, changed files, and limitations.

These rules reduce avoidable errors; they do not replace expert assessment of
dataset fitness, scientific conclusions, licensing, or real deployment behavior.
