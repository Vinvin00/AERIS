Yes. I’d structure this as a serious 8–12 week engineering project, where every phase leaves the repository working. The goal is to avoid spending three weeks building infrastructure before you can detect a plane.

AERIS

Monocular Aircraft Detection, Tracking & Trajectory Estimation

Core objective: Given monocular optical video, detect and persistently track aircraft, estimate image-space size and motion, predict short-horizon trajectories, and quantify the uncertainty/error of those estimates against known ground truth.

The eventual pipeline:

Video / Camera
      │
      ▼
┌──────────────┐
│ Preprocessing│  OpenCV
└──────┬───────┘
       ▼
┌──────────────┐
│   Detector   │  PyTorch → ONNX
└──────┬───────┘
       ▼
┌──────────────┐
│   Tracker    │  Kalman + Association
└──────┬───────┘
       ▼
┌──────────────┐
│ State Est.   │  Position / size / motion
└──────┬───────┘
       ▼
┌──────────────┐
│ Trajectory   │  Future image-space position
│ Predictor    │
└──────┬───────┘
       ▼
 Metrics / Evaluation / Visualization

Later, the real-time side moves into C++, while Python remains responsible for training, datasets and evaluation.

Phase 1 — Dataset & annotation infrastructure

This is where you properly learn the dataset-management/QA part of the Quantum JD.

1.1 Choose datasets

You’ll eventually want a combination of:

real aircraft footage + annotated aircraft images/video + synthetic sequences with known ground truth.

Do not worry about getting the perfect dataset immediately.

Start with one dataset that provides aircraft bounding boxes.

1.2 Standard internal annotation format

Regardless of source format, AERIS should convert everything into one internal representation.

For example:

frame_id
timestamp
class_id
track_id
x_min
y_min
x_max
y_max
confidence

This matters because later you might consume multiple datasets.

1.3 Dataset validator

Build:

python -m aeris.data.validate

It checks:

* image exists
* image readable
* annotation exists
* bbox has positive area
* bbox within image
* class valid
* no malformed values
* duplicate annotation detection
* track IDs valid
* corrupted frames
* dataset split leakage

1.4 Dataset statistics

Generate:

Total images
Total annotations
Aircraft per image
Bounding-box size distribution
Class distribution
Image resolution distribution
Small/medium/large targets

Bounding-box size distribution will become particularly important.

1.5 Annotation visualizer

python -m aeris.data.visualize

Randomly sample annotated frames and render the boxes.

This is your first substantial OpenCV work.

Tests

test_invalid_bbox
test_out_of_bounds_bbox
test_missing_image
test_corrupt_image
test_duplicate_annotation
test_annotation_conversion
test_split_integrity

Phase 4 — Multi-object tracking

Now stop treating every frame independently.

4.1 Track representation

Each aircraft gets:

Track {
    id
    position
    velocity
    bbox
    age
    frames_since_seen
    confidence
}

4.2 Kalman filter

Implement the filter yourself.

Start with:

x=[c_x,c_y,v_x,v_y,w,h]

Measurements:

z=[c_x,c_y,w,h]

The detector gives noisy measurements.

Kalman predicts where the aircraft should appear next.

4.3 Association

Multiple aircraft means you need to associate detections with tracks.

Build:

Predicted tracks
       +
New detections
       ↓
Cost matrix
       ↓
Assignment
       ↓
Updated tracks

Start with IoU/distance matching.

Then use Hungarian assignment.

4.4 Track lifecycle

Implement:

Tentative
    ↓
Confirmed
    ↓
Lost
    ↓
Deleted

This sounds small but is essential to a decent tracker.

4.5 Tracking KPIs

Measure things like:

ID switches, track fragmentation, track lifetime, position error, association accuracy.

Milestone 4:

Multiple aircraft receive persistent identities and survive short detection losses.

Phase 5 — Motion & trajectory estimation

This becomes the core intellectual part of AERIS.

5.1 Image-space motion

For every aircraft:

x(t)
y(t)
w(t)
h(t)

Calculate:

vx
vy
ax
ay
bbox expansion rate
direction
angular movement

5.2 Camera calibration

Now learn actual CV geometry.

OpenCV calibration gives you the camera intrinsic matrix:

K =
\begin{bmatrix}
f_x&0&c_x\\
0&f_y&c_y\\
0&0&1
\end{bmatrix}

That allows conversion from pixels into viewing angles.

Now instead of:

moving 12 px/s right

you can estimate:

angular motion ≈ X°/s.

5.3 Direction estimation

Calculate image-plane heading.

        ↑
      ↖ ↑ ↗
    ←   ✈   →
      ↙ ↓ ↘
        ↓

Smooth it through the state estimator rather than calculating it from two frames.

5.4 Trajectory prediction

Start simple.

Constant velocity:

p(t+\Delta t)=p(t)+v\Delta t

Then constant acceleration.

Then compare them.

Do not immediately throw a neural network at trajectory prediction.

5.5 Prediction horizons

Benchmark:

100 ms
250 ms
500 ms
1 s
2 s

Measure prediction error at each horizon.

Example:

0.25s → 4.2 px
0.50s → 8.7 px
1.00s → 23.1 px
2.00s → 71.8 px

Milestone 5:

AERIS can detect an aircraft, track it and predict where its image-space track is likely to continue.

Phase 6 — Apparent size & range estimation research

Treat this as experimental, because monocular ranging is fundamentally ambiguous.

6.1 Angular size

Camera calibration + bbox dimensions gives apparent angular dimensions.

Output:

Angular width:  1.72°
Angular height: 0.48°

This is directly observable.

6.2 Size-change estimation

Track:

\frac{dw}{dt}

and

\frac{dh}{dt}

This gives evidence of whether the aircraft is getting larger/smaller in the image.

Classify relative motion:

APPROACHING
RECEDING
CROSSING
UNCERTAIN

6.3 Approximate range

Only when you have a reasonable assumption/estimate for physical aircraft dimensions should you attempt approximate range.

Importantly, output:

Estimated range:
1.4–1.9 km
Uncertainty:
±250 m

rather than fake centimeter-level precision.

6.4 Uncertainty model

Propagate uncertainty from:

bbox measurement + aircraft dimension estimate + camera calibration + tracking uncertainty.

This is a great technical component.

Milestone 6:

Apparent-size, angular-motion and experimental range/motion estimates with explicit uncertainty.

Week	Main objective	Main thing you learn
1	Repo + dataset pipeline	pytest, OpenCV basics
2	Detector baseline	CV + PyTorch
3	Fine-tuning + evaluation	ML evaluation
4	Video + tracking	OpenCV + Kalman
5	Motion + trajectory	State estimation
6	Camera geometry + apparent size	CV geometry
7	Ground-truth evaluation	KPI design

9	Finish C++ + GoogleTest	Production engineering
10	Robustness testing	CV research
11	ONNX/TensorRT	Edge ML
12	Benchmarks + docs	Research communication

Don’t treat 12 weeks as a deadline. It’s the order of attack.

This matters because otherwise AERIS could expand forever.

I’d call AERIS v1.0 finished when you can run:

aeris input.mp4

and receive:

output.mp4
tracks.csv
metrics.json
benchmark.json

where the video shows:

             previous trajectory

And separately:

produces quantitative results for:

detection + tracking + trajectory prediction + robustness + latency.

That gives you a coherent flagship project instead of a pile of technologies.

And importantly, it complements your existing missile-guidance project rather than duplicating it: that project demonstrates 6-DOF simulation, PyTorch guidance, Kubernetes/CI and 236 automated tests; AERIS adds computer vision, OpenCV, C++, camera geometry, tracking/state estimation and edge inference. By the end, the technical story on your CV becomes significantly stronger: one project asks “where should the autonomous system go?”, while AERIS asks “what does the autonomous system see, and how reliably can it estimate motion from that perception?”
